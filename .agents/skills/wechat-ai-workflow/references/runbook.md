# 公众号执行与交接

## 开始或接续

1. 先读 [工作流入口](../SKILL.md)、[编辑准则](editorial.md)、[写作训练](writing-training.md)和[最新编辑反馈](../../../../EDITORIAL-HISTORY.md)，再确认这次的稿件、时间范围、交付路线和授权。开稿记录写明本篇沿用哪些意见。选题未定时按[选题目标、目的与方式](#选题目标目的与方式)采集与筛选，已有明确选题时直接记录已选。若已有微信草稿且用户手工编辑过，先让本地正文对齐用户认可的版本，再继续修改。当前版本无法取得时标明这一点。
2. 每篇用一个稿件目录。新稿记录北京时间日期和主题短名，有雷达选题时记 ID。目录可放在仓库的 `exports/`，可公开复用的脱敏样例放在 `examples/`。Agent 换机时需要可访问该目录或完整稿包。
3. 写 `run.md` 记已定的题目和范围、当前正文相对路径及 SHA-256、各阶段产物和反馈、下一步及待解决事项。用了 WeWrite 就再记 `WEWRITE_HOME` 和任务 ID。接续时，从首个未完成或本轮最早受影响的阶段开始。正文变化时更新版本，重做受影响的审稿和交接产物。
4. 分工时协调者负责维护 `run.md`、版本合并和平台交接。采集和搜图可并行，写作和审稿在同一稿件上依次进行。同一时刻只有一个 Agent 修改正式 `article.md`，账号写入也由一人负责。每位接手人读本入口、自己的参考和上一步产物，不依赖聊天内容。
5. 本地依赖见 [安装说明](../../../../README.md#安装和首跑) 和 [WeWrite 设置](../../../../WEWRITE.md#直接使用)。只装本次路线所需依赖。同一 WeWrite 状态目录的 `current_run` 是共享指针。并行任务显式执行 `wewrite run show <任务-ID>`、`wewrite sources list --run-id <任务-ID> --json`、`wewrite run step <步骤> <状态> --run-id <任务-ID>`。无法指定任务 ID 的调用串行处理，或各自用独立的状态目录。

## 每篇执行顺序

1. **开稿检查。** 获取已配置的 GitHub 分支最新版本，回看近期用户反馈和本篇适用规则。把要沿用的偏好、选题状态与交付目标写进 `run.md`。接续稿同时读当前正文、核查表和上一版产物。
2. **采集与选题。** 选题未定时，按[选题目标、目的与方式](#选题目标目的与方式)找出 5–10 个热点，先看观众对各题的兴趣，再结合公众号主题挑出三张选题卡。已有明确题目时，记下用户已选的题和范围。已有雷达 ID 时回读选题卡，选题获批准后才进入 WeWrite 撰稿或审稿。
3. **核查与取材。** 建 `evidence.md`，把关键主张、数字、引语和限制对应到一手来源。看原文有无值得留下的短摘、X 有无能带来新细节的原帖、原文或馆藏有无可直接下载的原图。给用户看的内容可以是一条最有价值的新线索、候选素材和出处。核查与找图可并行。
4. **角度和结构。** 用一句话讲清读者为什么点开、看完能多知道什么。写出首屏和要展开的几个关键动作，每节对应一项发现。展示切入点和主线，让用户可以在正文成形前纠正侧重点。
5. **正文初稿。** 按[写作模块](../../wewrite-write/SKILL.md)和编辑准则展开，用原文、X 截图和原图支撑具体段落。人物、数字和时序写清归属，说明融进正文。展示初稿或本轮重点试写，记录用户对语气、篇幅和论点的意见。
6. **标题、封面与图文排版。** 走[标题模块](../../ai-title-generator/SKILL.md)的公众号档，看一眼能不能认出主角、实际动作与结果。若 AI 是主角，将具体产品或模型靠前，有真实且有冲击力的数字就优先使用。标题的承诺要在首屏兑现。给出主标题和封面预览，需要比较时再给备选。按[用图方法](#原文和图片)放图，手机宽度看裁切、字幕、图注和留白。
7. **审稿与交付验收。** 依[审稿模块](../../wewrite-review/SKILL.md)核对事实、引语、标题和全文，按需用 `wewrite content-eval` 辅助。检查标题、摘要、作者、封面、阅读原文和排版，用实际复制粘贴验富文本。展示本地审稿页、证据与验收结果。
8. **复盘并优化。** 按[每篇复盘](#每篇复盘)完成一项可核验的改动。若改到正文、标题、图片或排版，回到对应环节直接改并复验。按[每轮同步](#每轮同步到-github)确认 GitHub 版本，再交回最终文件。需要外部交付时，按[已选择的路线](#交接到微信或秀米)交付已复验版本。

### 选题目标、目的与方式

**目标**　抓取今天最火热的话题、观看人数最多的内容，以及场面或情节最火爆、能吸引观众观看的内容。可关注黄仁勋与股票、OpenAI、Anthropic、反重力（Antigravity），也看 DeepSeek、Kimi、GLM 等国产 AI 的颠覆性创作。这些是例子。搜索可以拓展到其他热门人物、产品、作品或事件，找观众正在热议、愿意看的内容。

**目的**　留住观众，做出他们爱看的东西。

**方式**

1. 先看 X（Twitter）、YouTube 上的原帖、视频与讨论，也主动拓展到有相关帖子和讨论的平台。以北京时间当天为优先，向临近时段找 5–10 个最火爆的话题，同一事件的多个信源并在一项里。
2. 再看观众对每个话题的兴趣。打开原帖、视频和讨论，记录可见的观看或播放量、评论或转发及核对时间，回看观众在热议、追问或转发哪个具体场面。按平台原样记录指标，查不到的标注未公开或未核实。
3. 然后结合「信号之外」的主题选题。先看观众愿意点开什么、哪一处能让他们继续看，再回查一手出处核对可写的事实。可用雷达和定向搜索补查。把热度依据和三张入选简卡交给用户选定，再进入正文。

### 各阶段怎样听取意见

- 进入下一阶段前看用户的最新消息。每完成一阶段，给用户看一份具体产物，简短交代本轮取舍。用户可以随时对题目、证据、角度、正文、标题、配图、审稿或交付提意见。
- 在 `run.md` 写清「用户原意、落实在哪、怎么复核」。一篇稿的选择留在本篇，用户明确的长期偏好或已验证可复用的做法写进合适的准则，再在[编辑反馈](../../../../EDITORIAL-HISTORY.md)记日期和案例。用户调整意见时同步修改旧规则，后续以最新表述为准。
- 每轮意见、修改或优化完成复核后，同步相应的反馈记录与改动，依[每轮同步到 GitHub](#每轮同步到-github)读回远端结果。
- 意见影响已完成阶段时，回到最早受影响的一步，把后面的相关产物一起更新。选题未定、用户指定需要确认或涉及外部交付授权时在对应节点等答复。其他环节展示阶段结果后，按已经明确的范围继续。

### 原文和图片

- **原文短摘**保留能支撑关键动作或差别的一小段，标清出自哪里。正文在有信息可补时接着写。
- **X 原帖截图**用于呈现原帖中的说法、实测或作者动作。打开原帖截取带作者和上下文的连续区域，保留链接，在手机宽度下验字。
- **直接下载的原图**从原文、原帖附件、官网或馆藏下载实际文件，存进本地素材目录再排版。用户点选图片时用其选定的版本，记录原帖、下载链接和可查的源头。
- 按稿件所需选素材。图紧跟它能支撑的段落，图注简写内容和出处。说明有新信息才写，放回自然叙事中。

三张选题卡各写主题、平台热度及观众在关注什么、对读者的影响、能吸引观众的场面或稿件角度、可用配图和一手链接。正文写作前把关键主张逐项对应到来源。术语、口径、引语或图表有改动时，把对应材料一起更新。在文末留能支撑主线的少量出处，完整资料进入 `evidence.md`。

遇到时效、财经或监管题时，把宣布时间、事件生效日和市场交易日分列，量化跨度按同一口径复算。第三方公开发言回看原帖或可溯源转载，正文写清身份和发言所指。只找到存档或媒体嵌帖时，在核查表注明。行情图依据已核对的实际记录绘制，过程图按日期区别决定、公告和待发生事项。

### 每篇复盘

从本篇用户反馈或实际遇到的问题中选至少一项改进，当轮落实并核验。没有新反馈时，以本篇可观察的结果为依据，比如旧图在手机上字太小，换成窄版原帖截图后仍能读到账号和关键段落。记录结论的适用场景，读者表现等到获得发布数据再判断。

`run.md` 留四项信息。可以合在一两段中。

- **反馈或问题**　用户说了什么，或在哪一步发现了问题。
- **前后变化**　实际改了什么、在哪个文件或环节。
- **核验结果**　怎么复看，结果是什么。
- **下篇沿用**　哪项改法值得复用、记进了哪条规则。

## 每轮同步到 GitHub

1. **读取远端。** 开稿或接稿时获取最新提交。检查本地未同步改动，按普通 Git 合并保留相关内容。以仓库的实际可见性决定可同步范围。
2. **把修改写到原处。** 每轮反馈都留下日期、意见摘要、实际改动及验证结果。已纠正的规则直接改或删，重复步骤合并到执行手册，其他页面链接到对应条目。用普通提交保留修改历史。
3. **提交并推送。** 核对差异，只暂存这一轮的工作流规则、反馈记录和可归档的修改。公开仓库提交工作流、经整理的反馈、改法和验收结果。稿件包、聊天原文、账号信息和待确认刊用权限的素材保留在本地。用户授权公开的稿件和素材按授权范围归档。每轮复核通过就提交并推送到已配置的分支。
4. **读回确认。** 用 `git ls-remote` 或 GitHub 接口读回远端分支，确认包含本次提交。在对应制作记录留提交号，交付时给出 GitHub 提交链接。同步失败时保留本地提交，记录待同步的原因。

## 交接到微信或秀米

### 微信公众号审稿页

默认准备本地可复制的审稿页和图片包，无需登录。先安装 [WeWrite 依赖](../../../../WEWRITE.md)，再从仓库根目录执行。摘要、封面和输出目录必填，封面参数相对于稿件所在目录。署名按用户已确认的名称填。原文链接选与本篇主线直接相关、可访问的公开一手出处。署名或原文链接无法确认时，对应参数可省略。

```powershell
python -X utf8 wechat_handoff.py examples/nvidia-2026-11-24/article.md --summary "离任11天，黄仁勋全票复职。董事会五天内改口，英伟达收涨31.48%。" --author "信号之外" --cover images/cover.jpg --source-url "https://nvidianews.nvidia.com/news/nvidia-board-reinstates-jensen-huang-as-president-ceo-and-board-director" --out exports/nvidia-review
```

在输出目录确认 `review.html` 和 `handoff.json`。查清单中的标题、摘要、署名、原文链接、封面、按正文顺序记录的图像路径及正文和预览的 SHA-256。对比图片顺序、正文首尾和最新正文，检查引用链接与公开原文分栏。打开审稿页看手机宽度。点击复制后，用本地页验证实际剪贴板含 `text/html`，且图片数量和小标题与审稿版一致。只看到复制提示、纯文本或旧剪贴板内容时，继续验证富文本来源和接收端。

站点访问或账号权限受限时按人工交接。运营者先把富文本粘贴到正文，分别填写标题、摘要、作者和原文链接，再从审稿页下载封面上传。正文第一张和清单中的封面相同时，也可在编辑器中从正文选第一张。粘贴后预览确认图片真实加载、裁切和段距。

### 微信公众号官方草稿

用户要求草稿交接且账号管理员已授权并配置时，按 [WeWrite 草稿说明](../../../../WEWRITE.md#交给运营者在公众号编辑页终审) 执行。网页登录与接口配置分别完成。AppID、AppSecret、IP 白名单或素材和草稿权限未就绪时，继续交付本地富文本。只使用官方接口，凭据从本机账户配置读取。WeWrite 4.2.0 的 `publish` 子命令实际创建草稿，核对调用范围后再执行。取得真实稿件 ID 后用官方读取端确认标题、摘要与正文图片。该命令没有原文链接参数，编辑页另外设置并核对「阅读原文」。有请求超时或平台返回不确定时先核对草稿，确认结果后再决定是否重试。

### 秀米

用户选择秀米时按 [秀米交接说明](../../../../XIUMI.md) 批量导入。读取当前账号可用入口。Word 导入会重新排版，图文先一次导入，再单独设置标题、摘要和封面。保存后重新打开同一图文，通过预览检查图片、段间留白、首尾和来源。公众号同步需要独立授权，保存到秀米即记为秀米稿。

## 怎么记录已完成

下表各步骤按实际证据写入 `run.md`。保留已使用工具、正文版本和下一步，具体账号回执只留在获准保存的位置。

| 可以报告的状态 | 证据 |
| --- | --- |
| 已审稿 | 当前正文和对应版本的审稿报告，事实、图表和措辞已核对。 |
| 本地包已验收 | `review.html`、`handoff.json` 与本轮检查，说明预览以及富文本验证的实际结果。 |
| 秀米已保存 | 保存成功，重开指定图文并核对关键内容。 |
| 公众号草稿已创建 | 获得真实公众号草稿回执，回读同一草稿校验。未配置接口、模拟运行和截图中的预览各自记录原状态。 |
| 运营者已预览或发布 | 分别记录由运营者明确确认的状态和日期，或可核实的正式发布结果。预览页只证明预览。 |

当前步骤交接时，最小文件集为 `run.md`、`article.md`、`evidence.md`、`titles.md`、审稿报告、封面和正文素材、对应交付物。归档使用相对路径，将正文和资产一起保存。账号秘密、登录态、可识别的临时预览链接不进稿包或 Git。按 [复盘与恢复](../../../../EDITORIAL-HISTORY.md) 保存可复用的规则和已授权归档的样稿。
